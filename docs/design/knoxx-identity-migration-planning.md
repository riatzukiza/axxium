# Complete Knoxx identity migration planning

Authored proposal for [Axxium issue 6](https://github.com/open-hax/axxium/issues/6) and existing UUID `axxium-knoxx-identity-migration`, Todo/P0/8. The original card's six requirements and four acceptance criteria are unchanged and controlling. All decisions below require planning review and lawful owner admission before implementation. A plan is not accepted token policy, native Ready, a live identity service, or deployment authority.

## Source authority and current behavior

Axxium accepted/personal-main `2439d4d6b8e546cda276f09f5c96db59226ecad6` supplies `schema.cljs`, `auth/token.cljs`, `auth/session.cljs`, `routes/auth.cljs`, `routes/actor.cljs` and `shape/db.cljs`. It has email/password login/signup and session-backed `/api/auth/me`, actor routes, PostgreSQL session hashes, and HS256 JWT creation/verification configured with issuer/audience. Flat SQL rows and namespaced schema/claim keys differ, so the future boundary needs explicit tested normalization; shape declarations alone do not prove runtime compatibility. OAuthClient schema, config flags and route docstrings do not establish an implemented OAuth authorization server. Kernel design documents describe conceptual capabilities; those claims do not qualify deployed auth behavior.

Knoxx accepted `3409977bca4ba35e09967f9a99d50867a679a73c` is inspected in a separate complete Git store. Its current source corrects the historical paths in the original card:

- `backend/src/cljs/knoxx/backend/extern/axxium_authority.cljs` admits only an operator-configured HTTPS origin, no userinfo/path/query/fragment.
- `domain/auth/axxium.cljs` and `law/axxium_identity.cljs` normalize the actor, bind exact issuer plus actor ID and reject email collisions without matching subject. `infra/auth/axxium.cljs` sends login only to that authority, forbids redirect following and imports neither passwords nor remote roles/capabilities into local directory privileges.
- `infra/routes/auth.cljs` delegates local login when enabled, disables local signup then, but creates a Knoxx session from the returned actor and Knoxx policy context. Other local/GitHub/invite/bootstrap/API-key and MCP auth paths still need a full admission inventory.
- `infra/auth/session.cljs` persists its own session state through policy storage and injects request context; `infra/auth/auth_session.cljs` is a compatibility alias and `infra/auth/authz.cljs` contains real tenant/resource/tool/conversation permission obligations.
- Mounted `frontend/src/cljs/knoxx/frontend/auth/boundary.cljs` in `app.cljs` calls `/api/auth/context` with cookie credentials and shares context with remaining TS consumers. Historical `AuthContext.tsx` is not the current entry point.

`backend/test/cljs/knoxx/backend/axxium_identity_test.cljs` already insists remote roles/passwords are not copied and email collisions/inactive subjects refuse. Preserve these protections during coexistence; introduce a reviewed restricted capability input rather than contradicting existing tests by silently granting remote roles. No consumer source is changed here.

## Proposed pure contract and effect ownership

Portable `.cljc` shapes/laws receive Clojure maps representing verified issuer/subject, session/actor status, capability evidence, tenant/membership facts, migration mappings, explicit clock/freshness and rollout state. They decide admission, effective authorization, conflict handling, migration progression and retirement eligibility. They neither fetch tokens nor inspect JavaScript, environment, cookie objects, DB rows or network responses. Use reusable Malli shapes at both replaceable boundaries. No new application board/FSM or receipt authority is proposed.

Axxium owns actor/entity identity, login/session verification, capability grants/revocation and subject-migration binding contracts. Its named extern adapters own JOSE, BCrypt, PostgreSQL and HTTP conversion; ordinary infra coordinates effects after law admission. Knoxx owns a CLJS-first consumer adapter and its business policy; its named externs decode HTTP/client values and build trusted request context. Existing frontend TS boundaries may remain but cannot introduce backend TypeScript domain authority. Services owns deployment topology, ingress and private operator configuration. Provider credentials, signing keys and password material stay outside planning/receipts and trusted publisher inputs; they never enter candidate CI or a browser projection.

### Login and browser session decision

Propose same-origin browser auth routing to the configured Axxium service: Axxium login issues its own HttpOnly session cookie, and Knoxx's context hook validates that session through the reviewed Axxium contract before resolving local resource policy. This requires a reviewed routing/ownership agreement; it is not permission to modify ingress here. Do not assume a cookie set by one unrelated host is readable or sent to another. Review Secure, SameSite, Path/Domain and expiry, origin/CSRF controls for every mutation, trusted forwarded-host handling, public configuration allowlists, credentialed CORS if an alternative is chosen, return-target allowlists and logout/session revocation before code. JavaScript sees a sanitized context and error/loading state, never credential cookies or raw bearer tokens.

The actual Axxium login API is the concrete initial boundary. Any selected OAuth path needs explicit provider callback/state/identity-linking and authorization-grant decisions and tests before replacing Knoxx GitHub callbacks; current flags are not that proof. Cover signup, invitations, bootstrap administrator rotation/revocation, machine/API-key/MCP and background auth in the original all-flows outcome. An Axxium denial, timeout, malformed reply or unknown origin must not fall back to a local password or header-based principal. Accepted coexistence is explicit and temporary; final qualified mode routes every existing authentication entrypoint through Axxium.

### Bearer verification decision

Select and version exact issuer/audience/allowed algorithm and key trust, expiry/not-before/skew, token kind, actor/session lookup and revocation/freshness behavior. The proposal is Axxium-owned verification/status evidence delivered by a fixed, authenticated outer adapter; Knoxx does not accept a self-selected token issuer or arbitrary URL and does not receive the issuer's signing key merely to simplify HS256 verification. If offline verification is selected later, its key-distribution/revocation limit must be separately reviewed; existing HS256 code is not an approved consumer trust design.

Normalize verified row/claim data into a closed context, including source authority and actor/entity IDs. Reject malformed/multiple credentials, empty Bearer, conflicting cookie and Bearer subjects, wrong issuer/audience/key/algorithm, expired/not-yet-valid/revoked tokens, inactive actors, invalid schemas and unavailable status evidence. Token verification precedes local policy and every effect. Strip untrusted `x-knoxx-*`/payload principal slots before constructing authoritative request context. Preserve separately reviewed machine and MCP grant constraints; bypassing identity via a caller-supplied header or implicit admin default cannot satisfy all-flows acceptance.

### Capability and policy decision

Use fresh authenticated Axxium actor capabilities as a mandatory input to a reviewed explicit mapping to Knoxx permissions. Do not treat free-form role names, email identity, UI state or returned claims alone as authority. Effective access is bounded by both mapped capabilities and current Knoxx tenant/membership/resource/tool policy. Missing mapping/evidence, disabled membership, revoked capability or cross-org/resource mismatch refuses before effects. Local policy may restrict but must not invent an Axxium grant. Existing administrative bypasses, explicit actor bindings, API/MCP grants, conversation/run access and background actor authority require a reviewed compatibility table and regression controls before moving existing `authz` behavior to policy owners. Session/cache invalidation must make revocation observable within a reviewed bounded freshness contract; no indefinite cached grants.

### Existing users and migration decision

Inventory actual Mongo identity/credential/session collections and bootstrap/index/writer paths alongside resource attribution, memberships, actors and external provider subjects. Propose a versioned immutable migration binding keyed by exact source instance/user ID and target Axxium authority/entity/actor, with an idempotency key and proof provenance. Email normalization helps discovery but never authorizes linking. Pre-existing Axxium subjects, same-email different people, disabled users, multiple-org membership and concurrent import/login require explicit conflict holds without overwrites or privilege upgrades. Preserve business resource IDs, ownership, actor attribution, memberships and authorized access; distinguish a non-authoritative resource projection from remaining authentication storage.

Existing users must log in without re-registration. Password users require a reviewed verified credential-compatibility path (for example Axxium-owned legacy-hash verification followed by rehash after successful login) or another proof-backed continuity path; Knoxx uses scrypt and Axxium BCrypt, so copying a hash into the current BCrypt field is not a migration. Provider-only users require a proof-bound existing provider-subject link; emails alone are insufficient. Bootstrap/service/API-key users require explicit current credential/actor continuity and rotation/revocation tests. Decide secure transfer handling, supported algorithms/versioning, inactive-account behavior and rollback before implementation; no raw credential export is authorized by this document. A conflict is a held migration, not a forced new signup.

Plan dry-run inventory first, then idempotent import/binding in owned transactions, compare source counts and attribution, support retry after partial failure, and record progress/conflict checkpoints without secrets. Review concurrency and unique indexes so repeated import/login cannot create two target identities. Coexistence must have explicit allowed modes and owner-controlled cutover criteria; it cannot stay indefinitely as final acceptance. Prove rollback before destructive removal: revoke new sessions as needed, preserve mappings/history, restore the previously qualified auth route from a tested recovery point without resurrecting revoked privileges.

### Retirement decision

After full migration and integration evidence, switch final admission/UI to Axxium, reject old local sessions/credentials, prove no auth writer/bootstrap can recreate them, then retire the `auth_session` compatibility surface and `authz` module by moving lawful business-policy checks to reviewed Knoxx policy owners. Remove standalone session/password/token authority, tables or Mongo collections and obsolete auth imports/routes/configs. Keep only explicitly documented non-authenticating resource/membership projections and historic attribution; do not relabel an active session or credential collection as a cache. Removal checks inspect writers/indexes/bootstrap, deployed schema and rollback window, not just deleted filenames. Original no-standalone-auth-tables acceptance remains mandatory.
