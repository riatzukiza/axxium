# Proxx identity migration: whole existing issue 8 plan

## Authority and observations

This proposal refines `axxium-proxx-identity-migration`; it does not implement it. The original card is retained verbatim as the body prefix with Todo/P0/8 and all six requirements/four AC. Axxium `2439d4d6b8e546cda276f09f5c96db59226ecad6` is the freshly aligned owning/personal default main. Proxx `88471efd7f8cd27f64fc733a1c31369f00a6d432` is independently inspected owning/personal default main, not an assumed staging candidate or Foresight integration pin. Routing metadata does not grant authority over another child's implementation or operations. Existing Axxium origin PRs 26/13 and personal PR 1 propose kernel work; their open status is not accepted source. Personal PR 2 covers Discord, and the separate issue 6 plan covers Knoxx. Fresh full open inventories found no whole Proxx migration plan; this is bounded evidence, not an assertion of exclusive chat ownership.

Accepted Axxium currently exposes email/password signup/login, actor context, JWT issuance/verification and persisted session hashing. `src/cljs/axxium/auth/token.cljs` binds configured issuer/audience with HS256; session verification additionally looks up the stored actor and unexpired persisted session; that query does not check actor status. `schema.cljs` declares actors/entities/capabilities/auth context/OAuth-client shapes. These observations do not prove a complete OAuth authorization server, GitHub identity bridge, machine token exchange, remote introspection/revocation or tenant capability contract for Proxx. The approved design must specify those requirements, then implement or consume their qualified owning-source capability before consumer cutover. Static accepted-source constraints also need explicit proof: the current auth route passes raw DB actor maps to session/token functions expecting namespaced actor keys; token verification alone does not establish the persisted-session lookup used by verify-session. The current session query does not itself prove active actor status, and capability mutation must be authorized beyond mere possession of a session. Require reviewed row-to-domain normalization, nonempty subject/entity binding, suspended/retired actor refusal, permissioned capability updates, and role/status revocation freshness. These are source observations and future negative controls, not an executed backend defect verdict. Default development key/cookie configuration is not production trust evidence. This plan does not distribute or inspect operational keys.

Proxx paths below are relative to its own 88471 source. Source archives in the verification packet identify exact bytes; not every archived source file has been semantically reviewed. `src/lib/request-auth.ts` distinguishes legacy administrator, tenant API key, UI session and optional unauthenticated callers. `src/app.ts` installs the HTTP hook, explicit bootstrap exemptions and a trusted-local federation bridge override. `src/routes/api/ui/ws.ts`, `bridge-sse.ts` and `request-log-sse.ts` independently resolve authentication. Replacing only the HTTP hook is incomplete.

## Admission, trust and policy

Review the full token contract: accepted issuer, stable subject and actor/entity identity, intended Proxx audience/resource, permitted algorithms and key distribution, expiry/not-before/clock bound, status, revocation and capability freshness. Candidate-controlled claims, self-selected issuers/keys or role strings are not authority. Unknown issuer/key/tenant, suspended actor, malformed capability or unavailable mandatory verification fails closed before prohibited effects. Do not turn cached stale identity into an indefinite allow fallback. Review session/token revocation consistency, streaming revalidation and revocation during an awaited operation; preserve already delivered protocol semantics without granting new unauthorized work.

Axxium owns identity and session laws and named extern crypto/DB/HTTP adapters. Proxx owns tenant/provider/model/resource authorization: pure portable Clojure data/laws where practical, existing `src/proxx/policy/*` and `resources/policies/runtime/60-tenant-enforcement.edn`, not new TypeScript policy. Map Axxium capabilities into a reviewed Proxx contract. A capability cannot expand the intersection of tenant membership, API scopes, provider/model/share constraints and authenticated actor privileges. `src/routes/shared/ui-auth.ts` currently has owner/admin decisions; migrate actual authorization behavior into the accepted policy boundary rather than merely wrapping these decisions in a new token parser.

Explicitly classify public/static/health/preflight/login/callback/refresh/logout bootstrap. Review which can be unauthenticated protocol operations and what state proof they require; the original all-request requirement stays unresolved until reviewers agree its exact protocol interpretation. An authenticated callback state does not mean anonymous arbitrary callback data is trusted. Final protected API/administration/WS/SSE/provider mutation cannot fall through legacy admin, tenant-key local-only identity, `allowUnauthenticated` or trusted-header shortcuts. Coexistence is versioned, bounded and observable; absent migration configuration must fail closed, not default to the old mode.

Pure identity/mapping/capability laws have zero I/O. Effectful adapters may perform explicitly authorized read-only resolution necessary to decide admission. Refusal forbids unauthorized reads and prohibited mutations/provider/session/tool effects; counters must distinguish permitted reads from writes. No I/O in pure Malli/law/shape code, no new generic JS interop outside named extern adapters, no second board engine.

## Proposed recovery authority and verification response contract

This clarification supplements step 7 and the earlier admission contract; it is a proposed owner-reviewed design, not accepted provider behavior or an implemented recovery mechanism. Axxium remains identity/session/status/capability authority through coexistence, cutover and recovery. Proxx owns the migration journal, tenant/product reference reconciliation and provider credentials. Reverting consumer code must not turn a pre-cutover local authentication snapshot into authority. Choose a reviewed recovery mode: retain Axxium-backed admission with a compatible consumer, or refuse protected operations until a forward repair restores that admission. A local credential fallback is not an implicit third mode. No copied password hash, tenant-key hash, OAuth identity or stale session proves equivalence to a current authoritative principal.

Before cutover, define a versioned migration epoch and authenticated change-provenance contract with per-authority watermarks/checkpoints. Bind mappings and recovery decisions to proven issuer/subject, old-ID attribution, migration version, operation identity and ordering. A watermark is a proposed reconciliation bound, not proof supplied by a candidate-controlled counter. Specify which qualified owning writer records each event, how incomplete/unknown provenance refuses recovery, and how transactions, idempotency and concurrent updates prevent lost or duplicated changes. Preserve an immutable audit of decisions; do not create another identity/session authority or change the board engine.

Inventory both pre-cutover principals and users created or invited after cutover, including pending invitations, accepted memberships and Axxium-only accounts with no old Proxx identity row. Recovery must retain their authorized access and product attribution without forced re-registration, identity duplication, replayed invitation acceptance or rerunning the first-membership owner/admin bootstrap. A stale backup must not delete or strand such accounts. Retained old-ID mappings remain non-auth projections only. Reconcile account creation, stable-provider-subject linking/unlinking, identity merges/splits only where explicitly approved, credential rotation, session/refresh revocation, actor suspension/deletion, capability/role changes, tenant membership/invitation/active-tenant changes, tenant API-key creation/rotation/scope reduction/revocation and client registrations through the authoritative post-checkpoint changes before enabling any recovered consumer. A mutable GitHub login/email, stale role or locally restored session cannot overwrite a newer identity or admission decision. Conflicting mappings, missing epochs/watermarks or unverifiable changes require owner reconciliation and fail closed.

Keep Factory/OpenAI/local/API-key provider accounts, pending OAuth/device operations, reauthentication identity checks, DID/usage/quota/provider-owner joins and tenant/product storage in Proxx. Recovery must rebind each reference and pending operation to the current admitted actor and tenant without moving provider tokens or local billing secrets to Axxium. Recheck current ownership/capabilities before completing callback/poll/refresh/removal; revocation during recovery cannot be undone by restored provider state. Preserve intentional restrictions and deleted/revoked credentials rather than replaying historical access. Review recovery before and after irreversible local table retirement, with owner-qualified backup/restore and forward repair evidence; physical backup success alone does not establish authorized recovery.

Axxium must own and qualify a versioned token/session verification or introspection contract before Proxx relies on it. Its typed response must bind issuer, audience/resource, stable subject/actor/entity, session/token identity, current actor status, permissioned capabilities and their freshness/revocation evidence to the actual request. Raw DB-row normalization and authorized capability mutation remain explicit kernel prerequisites. Do not infer this API exists from JWT verification or from a stored actor/unexpired-session lookup. Proxx validates the response shape and provenance before applying its own restrictive tenant/provider policy; signature-only acceptance and an unavailable-status allow fallback are forbidden.

Propose distinct public failure semantics for owner review: missing, malformed, invalid, expired or revoked credentials are authentication refusal (401); a verified active principal lacking current capabilities, tenant membership or resource permission is authorization refusal (403); a required authority that times out, is unavailable, returns malformed/unknown-version data or cannot establish current status/freshness is unavailable verification (503), with no protected effect. Suspended/retired actor classification must be fixed by the same provider-owned contract and applied consistently, never silently admitted or guessed from HTTP success. Preserve public error privacy without leaking account existence, key material or provider tokens. The exact versioned response/error contract, cache lifetime and streaming revalidation behavior need approval and positive/hostile evidence; these proposed codes are not claims about current Axxium routes.
